# Entry x Topology x Backend Matrix

Date: 2026-07-11

This experiment turns the close-baseline discussion into a reproducible matrix:

```text
entry strategy
  x graph repair/topology maintenance
  x graph backend
```

The main executed matrix uses the real SIFT1M-derived 100k dynamic workload:
100k initial vectors, 20k inserts, 10k deletes, 1k queries, 128 dimensions.

## Command

```powershell
python experiments\run_entry_topology_matrix.py --search-l 240 --per-query-l 240 --timeout 2400
```

Outputs:

## What Was Compared

Entry strategies:

| Method | Meaning |
|---|---|
| `nsg_ep` | NSG's original entry point |
| `fixed_medoid` | single fixed center-like entry |
| `static_density` | density anchors selected before drift |
| `gate_static_hub` | GATE-style static centroid hubs parsed from `results/sift100k_gate_adapter/gate_hubs.txt` |
| `gate_initial_hub` | GATE-style centroid hubs selected only from the pre-drift initial vectors |
| `query_entries` | GATE-like learned query-to-hub entries generated by a lightweight ridge selector |
| `online_density` | our online-maintained density-aware entry set |

Topology settings:

| Topology | Meaning |
|---|---|
| `no_repair` | initial NSG graph + local insert edges + deleted-node masking |
| `local_repair32` | same graph plus local KNN topology repair with degree 32 |
| `rfix_like_local64_proxy` | stronger local KNN repair proxy with degree 64; not paper-faithful RFix/NGFix |
| `hard_query_repair_proxy` | hard-query-guided vicinity repair proxy from stale-entry hard training queries; not paper-faithful RFix/NGFix |

Backend settings:

| Backend | Status |
|---|---|

| DiskANN/Vamana | included existing same-graph entry adapter results; not a no-rebuild dynamic DiskANN result yet |

## Main NSG Results at Search L=240

All rows reach the same or saturated Recall@10 inside each topology setting, so the important signals are average distance computations and p99 latency.

### No Repair

Baseline `nsg_ep`: Recall@10 `0.9997`, avg distance computations `3877.51`, p99 `3517 us`.

| Method | Recall@10 | Avg distance comps | Delta vs `nsg_ep` | p99 latency | Delta vs `nsg_ep` |
|---|---:|---:|---:|---:|---:|
| `static_density` | 0.9997 | 3848.10 | -0.76% | 3394 us | -3.48% |
| `gate_static_hub` | 0.9997 | 3803.99 | -1.90% | 3329 us | -5.35% |
| `online_density` | 0.9997 | 3824.03 | -1.38% | 2972 us | -15.48% |

Interpretation: static multi-entry hubs already help entry routing, but online maintenance gives the strongest tail-latency reduction in the no-rebuild setting.

### Local Repair32

Baseline `nsg_ep`: Recall@10 `0.9999`, avg distance computations `4011.50`, p99 `4665 us`.

| Method | Recall@10 | Avg distance comps | Delta vs `nsg_ep` | p99 latency | Delta vs `nsg_ep` |
|---|---:|---:|---:|---:|---:|
| `static_density` | 0.9999 | 3972.49 | -0.97% | 3960 us | -15.12% |
| `gate_static_hub` | 0.9999 | 3932.28 | -1.97% | 4190 us | -10.19% |
| `online_density` | 0.9999 | 3952.03 | -1.48% | 4834 us | +3.61% |

Interpretation: entry overlays still reduce average search work after local graph repair, but p99 is not monotonic for `online_density` under this repair setting.

### RFix-like Local64 Proxy

Baseline `nsg_ep`: Recall@10 `1.0000`, avg distance computations `4530.87`, p99 `5453 us`.

| Method | Recall@10 | Avg distance comps | Delta vs `nsg_ep` | p99 latency | Delta vs `nsg_ep` |
|---|---:|---:|---:|---:|---:|
| `static_density` | 1.0000 | 4477.83 | -1.17% | 5879 us | +7.82% |
| `gate_static_hub` | 1.0000 | 4441.14 | -1.98% | 5363 us | -1.65% |
| `online_density` | 1.0000 | 4459.45 | -1.58% | 3506 us | -35.70% |

Interpretation: under a stronger local-repair proxy, the graph becomes more expensive but highly accurate. Online-maintained entries still reduce average work and give the best p99 tail result in this run.

## Paper-Safe Takeaway

The result supports a careful claim:

> Entry-set maintenance is complementary to graph/topology repair. Static hubs
> and GATE-style entries help because entry quality matters; online density
> maintenance specifically addresses drift-induced entry staleness. It reduces
> average graph-search work across all NSG topology settings tested, and gives
> the clearest p99 gain in the no-rebuild and strong-repair proxy regimes.

What this does not prove yet:

- It is not a paper-faithful GATE run; `gate_static_hub` uses generated centroid hubs, not the learned two-tower GATE selector.
- It is not a paper-faithful RFix/NGFix comparison; `rfix_like_local64_proxy` is a stronger local KNN repair proxy.
- The DiskANN/Vamana rows currently prove entry-overlay orthogonality on a shared rebuilt graph, not full no-rebuild dynamic Vamana.

| `hybrid_hub_density_two_tower_e8` | 0.9997 | 3835.43 | 1705.05 us | 974.59 |

What improved:

- Adding graph hubness to density anchors helps. `hybrid_hub_density_static`
  reduces average distance computations from `3824.03` to `3798.82`.
- Query selector top-4 is better than top-8/16 for the GATE-style selector on
  this workload.
- Two-tower selectors tend to help p99/QPS more than average distance
  computations.

What did not improve enough yet:

- `gate_static_hub_upper` remains the best average-work entry set in this
  SIFT100k run. This reinforces that hubness/reachability must be part of our
  maintained entry objective.
- The current dynamic-density candidate set alone is not a strong enough
  candidate set for the two-tower selector.

Next algorithmic change:

> Maintain a hybrid entry set online: split/retire anchors using density and
> load, but score candidate anchors with graph hubness/reachability as well.
> Then optionally put a GATE-like query selector on top.

## Online Hubness-Aware Maintenance

Implemented mode:

```text
online_hub_density
```

Files:

```text
tools/nsg_dynamic_entry_runner.cpp
experiments/run_nsg_dynamic_entry.py
results/online_hub_density_eval/online_hub_density_summary.csv
```

Mechanism:

- Start from the same pre-drift `static_density` seed anchors as
  `online_density`.
- During streaming insert batches, select replacement/split candidates by:
  coverage distance to current anchors, local density, graph hubness/indegree,
  and a small inserted-region bias.
- Retire anchors that are both spatially redundant and weak graph hubs.

Best current no-repair setting uses `entries=4`, `maintain_sample=1000`.

| Method | L | Recall@10 | Avg distance comps | p99 latency | QPS |
|---|---:|---:|---:|---:|---:|
| `nsg_ep` | 240 | 0.9997 | 3877.51 | 3244.65 us | 667.42 |
| `online_density` | 240 | 0.9997 | 3826.70 | 1614.49 us | 903.94 |
| `online_hub_density` | 240 | 0.9997 | 3793.99 | 1691.93 us | 988.39 |
| `gate_static_hub` | 240 | 0.9997 | 3746.26 | 2329.17 us | 816.97 |

With local graph repair32:

| Method | L | Recall@10 | Avg distance comps | p99 latency | QPS |
|---|---:|---:|---:|---:|---:|
| `nsg_ep` | 240 | 0.9999 | 4011.50 | 2986.12 us | 673.94 |
| `online_density` | 240 | 0.9999 | 3956.61 | 2912.88 us | 612.37 |
| `online_hub_density` | 240 | 0.9999 | 3931.82 | 4626.84 us | 444.06 |
| `gate_static_hub` | 240 | 0.9999 | 3870.33 | 2581.41 us | 737.73 |

Interpretation:

- Hubness-aware online maintenance improves average search work over the
  previous density-only online maintenance.
- It composes with local graph repair on average search work.
- It still does not beat the refreshed/static GATE hub upper bound on SIFT100k,
  so the safe claim is improvement of online entry maintenance, not dominance
  over GATE-style hub selection.
- p99 latency is noisy across single runs; final paper tables should repeat
  runs or report per-query/hard-bin distributions.
